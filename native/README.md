# Native implementation notes

How the native application works internally. For what Rhino is, how to build and run it, and the user-facing feature list and shortcuts, see [the root README](../README.md).

## Layout

`src/` holds the application, and builds as three targets so that editing one part does not rebuild the others:

| Target | Holds | May depend on |
| --- | --- | --- |
| `RhinoCore` (`src/core/`) | Foundation with no engine or UI: `ContentLibrary` | JUCE only |
| `RhinoDevices` (`src/devices/`) | Rhino's plugins, under `instruments/`, `audio/`, `midi/`, plus `DeviceCatalog` | Tracktion, `RhinoCore` |
| `RhinoNative` (`src/`) | `Session`, the UI, the app shell | both of the above |

A device may not include `Session.h` or any UI header, and `Session.h` reaches the device library through `DeviceCatalog.h` alone. It used to include all six device headers, so editing any device rebuilt nearly every translation unit.

`src/tests/` holds the test runners and their scenario files — see [the test README](src/tests/README.md).

Content — samples now, presets and patterns later — lives in files under `library/` at the repository root and is **never** compiled in. JUCE expands an embedded asset to roughly three bytes of C++ per byte of data and recompiles all of it on a clean build; the 700 KB that used to be embedded became 2.1 MB of generated source, and a sample library of any size is unworkable there. `ContentLibrary::root()` finds it: the `RHINO_LIBRARY_DIR` override, then a `Library` folder beside the executable for an installed build, then the repository's `library/` for a development build. Audio under `library/` is stored with Git LFS. `assets/` is what remains compiled in as JUCE binary data, and is deliberately only the fonts and app icons — what the UI needs before it can read anything from disk.

`.deps/` holds pinned JUCE and Tracktion checkouts fetched by `scripts/fetch-dependencies.py`; it is ignored by version control and is not Rhino's code.

A class may be defined across several translation units. `Session` is implemented in `Session.cpp` plus the `Session*.cpp` files; `Arrangement` in `Arrangement.cpp` plus `ArrangementGeometry.cpp` and its siblings. Every source file is listed explicitly in `CMakeLists.txt` — nothing is globbed, so a new file needs a line there.

## Boundaries

- Tracktion owns edits, playback graphs, streaming, parameters and device state; the UI does not schedule audio.
- Utility's processing path uses an atomic parameter read and a preallocated smoother. It handles sub-buffer offsets and shares the same gain ramp across channels. Its stable type ID is `rhino.utility.v1`, with a `gainDb` parameter.
- Slider feedback happens directly in the control event path; gain gestures use the engine's automation hooks. A 10 Hz timer updates only transport text. The playhead uses JUCE's display-vblank callback and narrow damage strips at its old and new positions; note data stays cached between edits. The note ruler is outside these strips, and arrangement navigation updates the line immediately. Neither is an audio scheduler.
- Both playheads are blue and retain fractional-pixel positions. Each display refresh reads the audio graph's latency-adjusted audible position directly, bypassing Tracktion's 50 Hz transport-property timer. Stopped/scrub positions and immediate pending seeks remain responsive. Position precision still follows the audio processing cadence; this is not a claim of measured end-to-end display latency.
- The pinned Windows Direct2D renderer collects damage in `WM_PAINT`, but invokes vblank listeners before painting damage collected earlier. After moving a playhead, `Playhead.cpp` uses [UpdateWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-updatewindow) to submit its new damage before that frame is drawn. This avoids erasing the old line while clipping out the new one. The handoff is restricted to Windows Direct2D; macOS and the software renderer use normal JUCE invalidation. Recheck this adapter when upgrading JUCE. Regression checks cover the native damage handoff and compare incremental frames with full renders at 100%, 125%, 150%, and 200% scale; they do not measure live display frame pacing.
- The window draws its own title bar, but keeps the native frame styles. On Windows JUCE only gives a borderless window `WS_CAPTION | WS_THICKFRAME | WS_MAXIMIZEBOX` when the drop-shadow flag is set, so `Main.cpp` sets it: without it there is no Aero Snap when the caption is dragged to a screen edge, no snap-layouts flyout, and maximising covers the taskbar instead of stopping at the work area. The maximise button therefore maximises. Full screen is a separate thing, reached from View or F12: it is JUCE kiosk mode, which normally drops the title bar, so `Window` overrides `getContentComponentBorder`, `paint` and `resized` to put it back, and its maximise button leads back out.
- An audio clip's gain, pan, pitch, fades, mute and reverse are properties of the *clip*, not of its track: they live on the clip's `ValueTree` through `AudioClipBase`, so they travel with it, are undone with it, and leave its neighbours alone. `SessionAudioClips.cpp` is the whole of that API and `AudioClipPanel` the whole of its UI. A knob drag is bracketed by `beginAudioClipGesture`/`endAudioClipGesture`, which is what makes it one undo entry and one change notification instead of one of each per pixel - without it a fader pull rebuilt the arrangement's clip cache on every mouse move.
- Under the arrangement are **two independent panels**, and each answers to exactly one thing. The clip panel answers to the selected *clip*: a MIDI or drum clip puts the note editor in it, a double-clicked audio clip the audio clip editor, which then follows the audio clip selection as Live's clip view does, and selecting no clip closes it. The Device View answers to a clicked *track card*, and to nothing else. Neither reaches into the other - opening a clip leaves the devices alone, and clicking a card leaves the clip panel to the clip selection - which is what lets an audio track show its effect chain at all: it has no instrument, so under the old single-pane rule the rack was closed for it. `Arrangement` reports `clipSelected`, `clipOpened`, `trackSelected` and `trackFocused` and decides none of them: which panel a click belongs to is the shell's business. `trackFocused` exists because `trackSelected` reports only a *move*, and a click on the card already selected still has to bring the Device View back after it was closed; it is fired from the card-click paths only, so a clip click - which carries the working track with it - never opens devices. An empty strip is given back to the arrangement rather than left blank. The layout change itself is deferred to the 30 Hz timer and applied only once no mouse button is down, because the click that asks for it arrives from a mouse *down* - the same press that may be starting a clip or card drag, which resizing the lanes underneath would move out from under the pointer.
- There is one mixer, not one per view. Track volume and pan are a `VolumeAndPanPlugin` at the end of each track's plugin list, added to tracks restored from documents written before it existed; mute and solo are the track's own properties. The session view draws these as a vertical strip and the arrangement as a horizontal one, and both read and write the same parameters, so neither can hold a stale level. `UtilityDevice` is a device in a chain, like Live's Utility, and is deliberately not the fader.
- Clip launching is the engine's. `Session` only queues `LaunchHandle` state from the message thread; the audio thread decides when a slot starts and stops, and sets a track's `playSlotClips` itself once a slot is playing. Two rules are Rhino's rather than Tracktion's: a track plays at most one slot clip, so launching stops that track's other clips at the same quantised beat, and launching a scene stops tracks whose slot in that row is empty. Launch positions come from the playback context's sync point; before that context exists the first launch is immediate. The session view repaints from `SceneWatcher`, which notifies only when a slot's play or queue state actually changes. A track whose slot is playing ignores its timeline clips, so `returnToArrangement` clears that override; the control bar polls for it on the existing 30 Hz timer because the engine raises the flag from the audio thread without broadcasting. A slot clip and a timeline clip are separate objects: copying between them re-inserts wave clips from the same source file rather than duplicating media, clones MIDI sequences, and flips the loop range, since a slot clip repeats until stopped while an arrangement clip plays its own span once.
- Copy, cut, paste, duplicate and delete all act on a *region*: a span of time across a run of tracks in the arrangement, a span of steps in the note editor. That is one rule rather than four, and it is why the arrangement and the note editor behave the same. `Arrangement::effectiveRegion` resolves it - the dragged-out span when there is one, otherwise the span of what is selected - and `Session::copyClipRegion`, `clearClipRegion` and `pasteClipSnapshots` in `SessionRegion.cpp` are the edit side of it. `clearClipRegion` splits at both edges first and then deletes what is wholly inside, which is what handles trimming, cutting a hole and deleting whole clips without three cases. Paste clears the span it is about to occupy before it inserts, so it replaces what it lands on the way Live does rather than stacking on it; duplicate is paste at the region's own end, with the region carried onto the copy so a held Ctrl+D keeps extending. `Session::duplicateClip` is the same call on one clip's own span, which is what retired the old hunt for the first free gap.
- **Two clips may never overlap on one track**, and the clip that just arrived is the one that wins the ground it landed on - Live's rule. `makeRoomForClip` is the only place it lives: it splits what is already there at the newcomer's edges and removes the part underneath, so a clip dropped into the middle of a long one cuts a hole and fills it while the parts either side survive as clips of their own. Every path that places a clip ends there - `editClip` for drags, trims and nudges, `importAudioAt`, `insertPatternPreset`, `copySlotClipToArrangement` - and `pasteClipRegion` gets the same effect by clearing its whole rectangle first. `createClip` is the exception: a double-click on occupied ground is a mistake rather than an instruction, so it refuses. A multi-clip drag names every clip in the gesture to each `editClip` through `movingWith`, or the leading clip of a run moved one beat right would delete the one behind it.
- A copied region is a `ClipRegion`: its own width and height plus the clips that were inside it. The size is carried rather than measured back off those clips, because an empty lane or a trailing rest is part of what was copied even though no clip records it. Paste clears the whole rectangle before inserting, so pasting a region whose second lane was empty empties the lane it lands on, and the region left selected afterwards is the rectangle rather than the bounding box of what happened to be in it.
- A region read off the selected clips belongs to those clips and travels with them: `regionFollowsClips` makes `sync` re-derive it, so moving, trimming or nudging a clip carries its highlight along instead of leaving it at the old position. A region dragged out over the lanes belongs to the timeline and only has its rows clamped to tracks that still exist. A drag previews rather than editing, so `displayedTimeSelection` draws the region at the previewed geometry the way `displayedPosition` draws the clips; the commands keep reading `effectiveRegion`, which is the state the edit is actually in.
- A new document's `Pattern 1` is a placeholder - empty, and hidden from the arrangement by `shouldShowClipInArrangement` until it has notes. `createClip` therefore *places* it rather than refusing when it is the only thing in the way, because a hidden clip blocking the first bar made the starter track behave differently from every track added after it.
- The note editor draws its region as an insert mark and nothing else. The grid already has two ways of showing a selection - the marquee while it is dragged, and the notes it caught afterwards - so a band behind either of them reads as a third; what neither says is where a paste would land, which is the one mark worth keeping. `regionFromNotes` hides even that for a region read off the notes.
- The arrangement clipboard holds `ClipSnapshot` values, not clip ids: the source of a cut is deleted before the paste, and an undo between a copy and a paste takes it away too, so a clipboard that remembered where a clip *was* would paste nothing. A snapshot carries the source file for audio and the note list for MIDI, plus the position clamped to the region and the offset that clamping implies, so it can be rebuilt with the same `insertWaveClip`/`insertMIDIClip` calls everything else here uses.
- Deleting clips can take the clip the note editor is pointed at, and `Session::pattern()` dereferences that pointer. `repairPatternClip` is the single place that puts the editor back on another MIDI clip of track one, or makes a starter clip when there is none, and every path that removes a clip ends there.
- Arrangement clip geometry is cached between edit notifications. Waveforms share a thumbnail per source file, scan samples on JUCE's thumbnail worker, and repaint their own clip regions as data arrives. Pointer movement updates only a local preview; the engine edit and undo transaction change once on release. UI selection stores clip IDs rather than pointers that would become stale during undo or project replacement.
- Save serializes a detached engine snapshot on a background worker, writes a temporary file beside the destination, and replaces the target on success. Edits during saving remain dirty. Open parses off-thread, validates before replacing the active edit, and detaches UI listeners before releasing the old edit. Engine reconstruction still happens on the message thread; controls are disabled during open to prevent losing concurrent edits.
- No synthetic large sessions, capacity claims, or FPS benchmark harness are included. Frame pacing and pointer latency remain design requirements to measure later. Import metadata work still runs on the message thread and needs background preparation before the production browser grows.

- The main track wraps the edit's master plugin list rather than being a real track, and Rhino addresses it as one past the last audio track so the device, parameter and automation calls need no second code path. Its fader is the edit's master volume plugin, which is why the main level and pan read the same in the arrangement and the session view. Its row in the arrangement is pinned under the scrolling lanes, so `laneContentHeight` excludes it, and the timeline grid carries on through it. Lane rows have a floor height, so a short panel leaves rows hanging past that row: the track header controls are children of `laneHeaders`, a container spanning the lane viewport, and JUCE crops them at its edges rather than letting components draw over the main row or the ruler.
- A track card holds its own row height and colour, both on the track state, so they travel with the track when it is reordered and are saved with the project. `trackLaneHeight` returns zero for a track that has never been dragged, which is what keeps an untouched project fitting its rows to the panel; `laneHeightFor` resolves that, and answers with the live preview while a card edge is being dragged so a resize does not rewrite the edit per pixel. Height is a view setting and is written without an undo transaction; colour is one, because it is a decision about the track. Reordering is `Edit::moveTrack`, whose insert point names the track the moved one lands behind, so it is read from the order with the moved track already lifted out. `sync` lays the header controls out itself rather than leaving it to the next `resized`, because a track created by a browser drop or the add button would otherwise show a card whose buttons and faders are still sized at nothing.
- A track group is a bus, and the bus is an ordinary `te::AudioTrack`. That is the decision everything else follows from: the bus keeps its place in `getAudioTracks()`, so the mixer, the devices, the automation and the arrangement's own card drawing all reach it with no second code path, and it carries the group's name, colour, fader, mute and solo simply by being a track. Members are routed into it with `TrackOutput::setOutputToTrack`, which the engine allows in either direction in the track order, so the bus can sit above its members as it does in Live. What a bus refuses is what makes it a bus: `addDevice` takes audio effects only, and `createClip`, `importAudioAt` and `clipSlotAt` all turn it down, because a sum has nothing for an instrument to play and nowhere to put a clip.
- The structure is positional and nothing else: a bus is immediately followed by the run of tracks whose `rhinoGroup` matches its `rhinoGroupBus`. No member list is stored, so nothing can disagree with what is on screen. `reconcileTrackGroups` enforces that run after anything that reorders or removes tracks and *then makes the routing follow it*, which is the whole of the rule that a track carried into a group joins it and one carried out leaves it, with the audio following both. It asks `usesDefaultAudioOut()` rather than `getDestinationTrack() != nullptr` when sending a track back to the main output: deleting a bus leaves its members naming a track that is no longer there, which reads as no destination while still being one the engine resolves on every render - and an offline render of an edit in that state never returns.
- A collapsed group lays its members' rows out at *zero height* instead of dropping them, so `lane`, `bounds`, `cardAt` and the header controls all answer with an empty rectangle and draw nothing without a hidden case of their own. Groups do not nest: grouping refuses a selection containing a bus, and `reconcileTrackGroups` never makes a bus a member.
- Documents written before a group was a bus carry a `rhinoTrackGroup` node on the edit and a membership property on each track, with nothing to route to. `migrateLegacyTrackGroups` rebuilds them as real groups on load. Because a bus is a track in `getAudioTracks()`, `restoreProject` and `refreshUtilityPointers` no longer assume the pattern track is index 0 and the audio track index 1; both take the first two tracks that are not buses.
- Renaming a card or a band is in place rather than modal. One `juce::TextEditor` serves both, placed over `trackNameBounds` or `groupNameBounds` - the same rectangles the painter draws those names into, so the text does not move when it becomes editable - and the painter skips the name it is covering. It is a child of `laneHeaders`, so a row scrolled half out of view crops the editor exactly as it crops that card's buttons. `endRename` clears its state before hiding the editor and handing focus back, because both of those report a lost focus that would otherwise re-enter it; `sync` abandons a rename whose track or band has gone, since committing it would rename whatever took that index.
- Auditioning a library sound is a second `juce::AudioIODeviceCallback` on the engine's own `juce::AudioDeviceManager`, not anything inside the edit: JUCE sums its callbacks, so the preview mixes alongside the transport while choosing no track, writing no clip and opening no undo transaction. It is built on first use, so a session that never previews starts no thread and registers no callback, which is what leaves the test runs and offline renders untouched. It reads through a `TimeSliceThread` because the audio callback must never wait on a disk seek. `releasePreview` runs from both `releaseAudioDevice` and `~Session`, since either can come first and the callback has to be off the device manager while both it and the transport it reads are still alive. The on/off preference is a `juce::PropertiesFile` that `isCommandLineTestMode` suppresses, so a developer's setting cannot decide whether the suite passes.
- **A track declares what it is for, and one call answers.** `Session::TrackType` is `audio` or `midi`; `addTrack` writes `rhinoTrackType` onto the track state and `trackType` is the only place anything asks. Only `midi` is ever written: a track with no answer is an audio track, which is what every document written before this contains and why nothing had to be migrated. `trackType` answers `midi` for any track carrying an instrument whatever it was created as, so the property is a *declaration* the instrument can only confirm - and `switchTrackInstrument` writes it, so pulling the instrument back off leaves a track that holds notes rather than one that has quietly become an audio track with clips on it. Three gates read the answer and no longer ask about instruments themselves: `createClip`, `importAudioAt` and `trackRecordInput`. The gain from declaring it is that a MIDI track holds a clip before it runs anything, which is what every other DAW does and what the old rule - an instrument first, or no clip - could not express.
- Which kind to make is the user's choice, so the UI asks rather than the model guessing: `Arrangement::showAddTrackMenu` is on the `+` button and Ctrl+T in `Main.cpp` repeats the last choice. The choice is a `PropertiesFile` value beside input monitoring, not a document property, and `isCommandLineTestMode` suppresses it so a developer's setting cannot decide what the suite sees - a test run always reads the MIDI default. Only the menu records a choice; a track created by a drop below the last lane calls `addAudioTrack` and leaves the shortcut alone.
- Recording arms a **track**, not an input. What a track records follows from what the track already is: `Session::trackRecordInput` answers MIDI for a MIDI track, audio for an audio track, and nothing for a group bus or the main row. There is therefore no pairing for the user to make and nothing that can disagree with the rest of the document. The arm flag is `rhinoArmed` on the track's own state, so it travels with the track when the stack is reordered and is saved with the project exactly as mute and solo are; `applyRecordArming` rebuilds the engine's `InputDeviceInstance` destinations from those flags rather than letting the engine's copy become a second answer. It clears every destination and re-adds them instead of diffing, because a stale destination records into the wrong track. Audio goes to the default `WaveInputDevice`, MIDI to the default `MidiInputDevice`, and arming *enables* a device that was off - an input nobody had switched on is exactly the one just asked for. The MIDI device is put in replace rather than merge mode, so a take over an existing part is a new part.
- **A MIDI take is drawn while it is being played.** The engine writes no clip until the transport stops, so the lane would otherwise sit empty through a take and the whole part would appear at the end. `MidiInputDevice` keeps a short fifo of incoming notes per recording target, timestamped in edit time, for exactly this; `Session::pollRecordingNotes` drains it into spans and the arrangement draws them where the clip will be, in the colours and layout the clip will use, so nothing changes appearance at the moment the take becomes a clip. The band cannot be left to the playhead's own damage - that is two narrow strips at its old and new positions and not the span between them - so `repaintRecordingBand` invalidates what the band has grown by each frame, and the whole band only when a note starts or ends, which happens at the rate a person plays rather than at the frame rate.
- The **computer keyboard plays the MIDI input, not a track**. `ComputerKeyboard` maps the letter keys to notes and `Session::sendMidiInputNote` puts them into the chosen `MidiInputDevice`'s `keyboardState`, which is the same entry a controller's notes take - so by the time a note reaches a track nothing can tell where it came from, and arming, monitoring, Forge and recording all need no case for it. `Session::midiInputDevice` is the one rule for which input that is, shared with `applyRecordArming`, so what a note is played into is what a recording is captured from. The mapping is not Rhino's: it is `juce::MidiKeyboardComponent`'s default, `"awsedftgyhujkolp;"`, with Forge's own `12 * octave + offset` numbering and the octave limits Forge's key range implies - because Forge plays from that same default, and the surest way to keep two mappings identical is not to write a second one. Keys are matched with `juce::KeyPress`'s own `operator==` rather than by pulling a character out of the key code. That is what Forge does, and it is also what makes the match safe: `F9Key` is `VK_F9 | extendedKeyModifier` = 0x10078, and anything that squeezes that into a character gets `'x'` - which would have turned the record key into an octave shift. It is a `juce::KeyListener` rather than a Component's `keyPressed` because the keys have to be caught wherever focus happens to be, and because a listener is consulted *before* the component's own handler; a focused `TextEditor` consumes its own keys and never reaches a listener, which is what stops typing a track name from playing a chord. Notes are started from `keyStateChanged` rather than `keyPressed` so the system's auto-repeat cannot retrigger a held key, and `keyPressed` swallows the note letters so they do not also fire the shortcut they carry. Anything with a modifier is left alone, so Ctrl+C still copies.
- **Monitoring is Live's three settings, it belongs to the input, and it starts off.** `Session::InputMonitoring` is `off` / `automatic` / `on`, which is Live's Off / Auto / In and also, exactly, Tracktion's `InputDevice::MonitorMode`. Two things about it are Rhino's. It **starts off** where Live starts at Auto: `automatic` makes a live input audible as soon as a destination is record-enabled - as soon as a track is *armed* - and it stays audible until the track is disarmed, so on a machine with a built-in microphone and speakers Live's default is a feedback tone that outlives the recording. And it **belongs to the audio input, not to a track**: `isLivePlayEnabled` switches on the *device's* mode and the only per-track term in it is whether that track is armed, so a per-track mode is not expressible for tracks sharing one input device - and every audio track here records the one input. The track card's menu is therefore a shortcut to one setting rather than a per-card property, and shows the same answer on every card because it is the same answer. MIDI is always `automatic`: it cannot feed back, and an armed instrument track you could not hear would be useless. The preference describes the hardware in front of you rather than the song, so it lives in the same `PropertiesFile` as the browser preview rather than in the document. Changing it reapplies the arming, except during a take: `setMonitorMode` restarts the transports, which would cut a recording in half.
- The **count-in counts with the playhead standing still**, which is why it is Rhino's and not the engine's. Tracktion counts in by rolling the playhead backwards through the bars before the punch point: that caps it at the one and two bar counts its `Edit::CountIn` enum names, and it cannot count in at bar one at all, where there is no earlier time to roll from. `CountInClick` synthesises a decaying sine per beat instead, accented on the first beat of each bar, and mixes it through a second `juce::AudioIODeviceCallback` on the engine's device - the arrangement the browser preview already uses. `renderBlock` is the whole of the generator and is driven directly by `--self-test`, so the click spacing is checked without a device. The cost of owning it is that the transport is started from the message thread when the count ends, so the downbeat follows within about a block rather than on the exact sample; the click itself is sample-accurate. The setting is `rhinoCountInBars` on the edit, beside the other metronome settings, and it is offered in the metronome's own menu because that is what it is.
- **Recording does not need a clip to record into, and the take wins the ground it lands on.** The engine writes the clip when the transport stops and drops it on top of whatever was already on the track; `tidyRecordedClips` diffs the track's clips against the ids held before recording started and runs `makeRoomForClip` over the new ones, which is the same call every drag, trim and drop ends in. The diff is by id rather than by pointer because a recording can add clips to several tracks at once and making room for one can delete another. Recording also lifts the loop for its duration - Rhino loops the whole song by default, and a recording that wrapped would lay the next take over the one just played - and `refreshLoop` puts it back.
- The engine neither starts nor finishes a recording on the message thread and broadcasts neither, so the shell **polls** `Session::recordingStopped` on its existing 30 Hz timer, the same reason the session view's slot override is polled. `recordingStarted` exists because `record()` is asked for on the message thread and takes effect on the audio thread: without it the poll would read that window as a recording already over.
- `RhinoEngineBehaviour` is the only thing Rhino tells the engine about itself. It overrides `getFileForNewAudioRecording`, because the default naming pattern's `%projectdir%` resolves to nothing for a document that has never been saved and lands the take in the process's working directory, and `muteTrackContentsWhilstRecording`, because a recording covers what is under it.
- `Session::clickTrackGain` converts. Rhino talks about levels in decibels; the engine stores the click level as a linear gain and clamps it to 0.2 - 1.0. Writing decibels straight into it put all three of the menu's levels below that floor, so they were the same volume; the conversion lives at that one boundary.
- A track has one instrument, as in Live and Logic. `switchTrackInstrument` is the only thing that changes it: the replacement is inserted at the old instrument's index so MIDI effects stay ahead of it and audio effects behind it, and the instrument it replaces is removed rather than disabled, taking its patch with it. Clips are untouched, so switching an instrument leaves the pattern alone. Projects saved when a track could stack instruments are migrated on load by `collapseStackedInstruments`, which keeps whichever one was enabled. Nothing caches an instrument pointer, because switching invalidates it; ask the track through `trackInstrument` or `Session::patternInstrument`.

- `DrumDevice` has one parameter, `kit`, selecting a table of per-voice shapes: playback rate, an optional decay in seconds, and a level. It is read on the audio thread as a plain lookup with no allocation, and the Clap kit additionally routes the backbeat note to the clap pad. Kits are the same sample set reshaped, which is how a drum rack preset differs from another.

## Adding a device

Devices derive from `te::Plugin` and follow a fixed shape: a stable `xmlTypeName` (`rhino.<name>.v1`), the `getName`/`getPluginType`/`getVendor` overrides, and parameters wired through `referTo` / `addParam` / `attachToCurrentValue`, detached in the destructor and refreshed in `restorePluginStateFromValueTree`.

Registration is table-driven. A new device is three edits and no more:

1. the source under `src/devices/instruments/`, `audio/` or `midi/`;
2. a line in `src/devices/CMakeLists.txt`;
3. an entry in `DeviceCatalog.cpp`, plus its `createBuiltInType` line in `registerBuiltInTypes`.

The catalog entry carries the device's id, engine type name, display name, kind, browser group and blurb, its colour, and the pattern key that selects it. The browser rows, the drag-and-drop targets, the rack's add menu, the engine registration and the one-instrument-per-track rules all read it, so nothing in `Session` or the UI needs touching. `--self-test` asserts that relationship: every browsable catalog device must have a browser row and must be addable.

Do not make a device self-register from a static initialiser. Objects in a static library that nothing references are dropped by the linker, and the registration would vanish silently.

`Session::addDevice(id, track)` is the one way to add a device. `Session`'s `Instrument`, `AudioEffect` and `MidiEffect` enums remain as a typed shorthand for the devices that predate the catalog — presets and tests name instruments with them — and `DeviceIds.h` is the only place they become catalog ids. A device added from now on needs no enum.

## Dependencies

Pinned to the source-study Tracktion revision and its exact JUCE submodule revision. See `scripts/fetch-dependencies.py` for hashes. Upstream licence files are retained inside `.deps`; this does not change the licensing findings in the research.

The interface is drawn with Inter rather than the Windows shell font. `assets/fonts/` holds the Latin regular and semibold cuts, compiled in as binary data and served by `Theme::getTypefaceForFont`; `OFL.txt` beside them is the SIL Open Font License they are distributed under. JUCE's Direct2D backend renders text with greyscale antialiasing and no grid fitting, so the shell font goes soft at the sizes this interface uses, while a face drawn for screen holds its shape. Glyphs the Latin cuts do not carry, such as the transport symbols in the control bar, reach the system fallback as before.
