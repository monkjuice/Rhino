# A deck's bounce renders on a worker against a copy of the document

## Context

A DJ deck plays audio, not the edit ([DJ view and the booth](dj-view.md)), so a track or group of the song reaches a deck by being rendered to a file, a bounce, and is bounced again after every edit. The first version (commit `e4040dd`) rendered on the message thread, as Ctrl+J merge does (`SessionMerge.cpp`): a render reads the edit, and an edit changed under it from the message thread is a race, so blocking that thread was the simple way to be safe. Measured on 2026-10-09, one bar took 0.6-1 s with nothing repainting; a long track would have frozen the window for many seconds, on every re-bounce.

## The choice

Commit `363fd05`: the render runs on the booth's one worker thread, against a copy of the document loaded from a snapshot of its state (`Session::bounceDjDeck`, `native/src/SessionDjSources.cpp`). Since 2026-10-11 the state is built by `deckCopyState` and loaded by `loadDocumentEdit` (`SessionInternal.cpp`) with the role `te::Edit::forRendering` and the document's file in its `te::Edit::Options`, before it is built. This is the rule the file workers already follow ([Project files (.rhinoedit)](project-files.md)): a worker is handed a detached snapshot, never the live edit. The live edit stays on the device, so the decks and a track played Live are not interrupted, and the person goes on editing while it renders. When a deck bounces again is in [DJ view and the booth](dj-view.md): only for a change its bounce could hear, and never while a gesture is held.

Rejected: rendering the live edit from the worker (the race above), and keeping the render synchronous (the freeze).

## What it costs and what it requires

- **The copy holds only the tracks the deck plays**: a track deck's track, or a group deck's bus and its members (since 2026-10-11; from 2026-10-10 every bus came too). `deckCopyState` builds the state up after `mirrorAutomationToEngine` and `flushState`, so the copy carries the lanes as playback would: the edit's properties and every child except the `TRACK`s nobody plays (by `te::EditItemID::fromProperty(child, te::IDs::id)`), `MASTERPLUGINS` (the main chain, which the render leaves to the booth's mixer) and `rhinoDj` (the booth's own settings, which `projectSnapshot` writes into the live state). Built up rather than copied whole and cut down, the rest of a large song is never copied at all. The copy's plugins are still made again for every bounce, but only the bounced tracks', so a synth or a kit on another track costs the message thread nothing; the `bouncing` line in `rhino.log` carries the copy's time, 0.3-6 ms in the test documents. Making the copy and the `RenderTask` still happens on the message thread, which is why no bounce starts while a gesture is held ([DJ view and the booth](dj-view.md)).
- **A track deck's track plays as it sounds alone.** Its bus is not in the copy, so the track is sent straight out (`setOutputToDefaultDevice`, when its output named a bus: a destination the engine cannot find is one it never finishes rendering, [Offline renders that never return](renders-that-never-return.md)), and the deck does not change with the bus's fader or effects. Before 2026-10-11 the member was pointed back at its bus, which the copy kept but the render did not name, and the render failed at once with "Didn't find any audio to render": a track in a group could not be bounced onto a track deck at all (seen by running `DjBounces.inc` once against that routing). A group deck still renders its bus with its members, and there the routing must be set again: a track's output names its destination bus by its place in the audio-track list, not by id (observed: in the stripped copy a group member rendered straight out, at the same level before and after a −20 dB bus fader, where the full copy had routed it into the bus). So for a group `bounceDjDeck` points each member whose live track feeds a bus (`getDestinationTrack()`) at the copy's track carrying that bus's id with `setOutputToTrack`, before the `RenderTask` is made. `DjBooth.inc`'s "passes through the bus's fader" check caught it, and `DjBounces.inc` holds a track deck and a group deck on the same member against the bus fader ([Track groups (bus tracks)](track-groups.md)).
- **The song's mute and solo stay out.** `deckCopyState` removes `te::IDs::mute` and `te::IDs::solo` from every track it keeps: they say how the song is being listened to, and a deck is a channel of its own. Until 2026-10-11 a `te::FreezePointPlugin::ScopedTrackSoloIsolator` undid them for the render instead (it solo-isolates and unmutes the tracks it is given), so neither change is new to what a deck hears, and a mute or a solo is `ModelChange::none`: it bounces no deck.
- **For rendering, with its deck's id** (2026-10-11). Loaded `forRendering`, the copy can never be given a playback context, so Tracktion's device callback can never run its plugins beside the worker; a `forEditing` copy could get one, in the pinned engine's code, when an external plugin reported a latency change (read, not observed). The project id names the temp folder the engine keeps an edit's cached renders in and purges as the edit is built ([An edit's project id names its temp folder](edit-temp-folder.md)), so `deckCopyState` writes the deck's own id (`DjBooth::copyIds`, one per deck slot, made with the booth) over the live edit's: with the live edit's, building the copy purged the song's renders of every other track's clips; with a new one per bounce, as the first fix gave it, every bounce decoded, stretched or reversed its clips again in an empty folder and left the folder behind. A deck's first bounce still makes its renders, started by the clip's timer on the message thread (read, not measured); under the runners' inline render that timer never fires, so no scenario bounces such a clip. The booth deletes the decks' folders in `djReset` and `~DjBooth`.
- **A clip whose file is missing is refused** (2026-10-11). An offline render waits until every clip's file opens, muted or not, so one clip whose file has gone held the worker for the whole budget below. Before the copy is made, `bounceDjDeck` asks `checkClipFile` (`SessionInternal.h`) of every clip it will render - the deck's tracks' clips, or the slot's - and fails at once naming the file, which the deck shows. The fix for relative sources below made this common: a source stored beside the document used to resolve to no file at all in the copy, which the render skips, and now resolves to wherever the document is, which need not hold it after a Save As to another folder or a document moved away from its samples. `DjBounces.inc` deletes the reopened document's sample and requires the refusal well inside five seconds; Ctrl+J merge refuses the same way ([Offline renders that never return](renders-that-never-return.md)).
- **Told the document's file before it is built** (2026-10-11). A clip resolves its source while the edit is built and keeps it: `AudioClipBase::initialise` stores `sourceFileReference.getFile()` as the clip's current file, which `getAudioFile` and the render read. A source stored relative to the document, as every file imported after the document was opened from disk is, resolves through the edit's `editFileRetriever`, and the copy used to be given the live edit's retriever only after it was built: the clip kept an empty file and the bounce failed at once with "Didn't find any audio to render". `restoreProject` had the same order, so the reopened document played nothing for such a clip either; a probe saw the reference resolve and the current file stay empty. `loadDocumentEdit` passes the file in `te::Edit::Options::editFileRetriever` for both, and `DjBounces.inc` checks a document written to disk, reopened, and bounced before and after.
- **The bounce is a 32-bit float WAV** (2026-10-11), so a track driven past full scale reaches the deck as it is and the booth's gain does the rest; 24-bit stopped every sample at 1.0. JUCE's WAV writer at `37c894f` writes IEEE float at 32 bits when the sample format is left automatic, which is what the engine's writer leaves it (`AudioFileUtils::createWriterFor` at `4536d8a` passes the bit depth through), and dithering applies below 32 bits only. `DjBounces.inc` drives a clip 12 dB hot (its 0.7 peaks to about 2.8) and requires the bounce to hold peaks above 1.5.
- **`DjBounceWork` belongs to the message thread alone** (`SessionDjInternal.h`): the copy, a `ScopedClipSlotDisabler`, the `WavAudioFormat` and the `RenderTask`, declared so the render and the scope die before the copy. It is made in `bounceDjDeck` and destroyed in `djPoll` once the job has raised `done` (`releaseFinishedBounces`, which keeps a copy whose render did not finish while a newer copy of its deck still renders, since the two share a temp folder: [An edit's project id names its temp folder](edit-temp-folder.md)); the worker holds only a plain pointer to the render plus the shared `DjLoadJob`, and touches neither after `done`. `djReset` and `~DjBooth` drain the pool (`removeAllJobs(true, 10000)`) before dropping jobs and bounces, because a render still running reads a copy being destroyed.
- **A sixty-second budget.** A render that keeps returning unfinished would hold the only worker for good, so the loop gives up with "The bounce did not finish in time"; the job's `cancel` flag ends it sooner. Only a new source for the deck sets that flag (since 2026-10-10): a bounce asked for while the deck's own is still rendering marks the deck stale and returns, and `finishDjLoad` bounces again at landing, because cancelling under every edit meant a long render never landed while its devices were worked. The worker runs at `juce::Thread::Priority::low`, so a render no longer competes with the audio thread. The WAV goes to `%TEMP%\Rhino DJ bounces`, is read back with `readDjTrack`, analysed with the song's tempo as `knownBpm`, and deleted.
- **The test runners render inline.** Tracktion's render initialisation takes a `MessageManagerLock`, which a worker is granted only while the message thread dispatches. The app's always does, as it does for the WAV export; the runners have no dispatch loop (`JUCE_MODAL_LOOPS_PERMITTED=0`), so under `isCommandLineTestMode` the render runs on the message thread and `djPoll` installs it as before. The worker path is exercised only by the app, as the export's is.
- **The renderer fails at once, with "Didn't find any audio to render", when nothing in the job makes audio.** Two triggers remain. A group names its bus and the members that feed it in `tracksToDo`, because the engine builds a member into its bus's node and naming only part of that rendered nothing; `DjBooth.inc` checks the bus's own fader is in the bounce by turning it down and bouncing again. A MIDI track running no instrument has nothing to turn its clips into audio, so `bounceDjDeck` catches it before any copy is made and gives the deck silence instead (below). Two more went on 2026-10-11 (above): a grouped track routed into a bus the render did not name, and a wave clip stored relative to the document, which the copy, built before it knew the document's file, could not find. The probe that found the cause of the second met a trap of the runners: they reopen a document from a `juce::TemporaryFile` path that is never written, and the engine stores a source relative to a file that does not exist as if the file were a folder (`..\name.wav`, since JUCE's `getRelativePathFrom` uses the folder only of a file that exists) while its default resolver takes the path as the file's sibling, one folder too high ([Offline renders that never return](renders-that-never-return.md)). The app always opens a document that is on disk.

The render's parameters are a merge's: from the top of the song to the end of the last clip among the tracks, rounded up to whole bars and at least one, at the device's rate and block size, `usePlugins` on, `useMasterPlugins` off, 32-bit float stereo. The clips in the tracks' cells are kept out by the `ScopedClipSlotDisabler`, and the song's mute and solo are not in the copy. A deck on a clip slot (since 2026-10-10, [the console's clips grid](dj-view.md)) is the one exception: its span is that clip's own length, and before the render the copy track's timeline clips are removed and the slot's clip laid from the top in their place by `copyClipInto` with its loop dropped, the slot itself staying disabled like every other. A MIDI track with no instrument is not rendered at all (2026-10-10): once the span is known, `bounceDjDeck` cancels the deck's pending job, makes a `DjTrack` of silence of that span at the device's rate (48 kHz with no device), analyses it with the song's tempo as the known grid and no key detection, and hands it to `finishDjLoad` with the deck's generation and the `keepBeat` asked for, as if the worker had returned it; `rhino.log` says the deck holds N bars of silence. An instrument added later marks the deck stale like any edit, and the next bounce is real ([DJ view and the booth](dj-view.md)).

**A bounce carries the material's notes** (2026-10-10). Before the silent-track path and the copy, `bounceDjDeck` gathers the notes the render will play as `DjMidiEvent`s (`core/DjTrack.h`): a slot deck's clip from beat zero over the clip's length, else every MIDI clip the arrangement shows (`shouldShowClipInArrangement`) at its start beat; each note's clip-relative beat less `Session::clipOffsetBeats`, clipped to the clip's window; sorted by beat, a note-off before a note-on at the same beat. A group's bounce gathers none. They ride in `DjLoadJob::midi`, the worker moves them into `DjTrack::midi` beside the audio, and the silent bounce carries them too. The live preview plays them to the track's own instrument while a knob is held ([DJ view and the booth](dj-view.md)).
