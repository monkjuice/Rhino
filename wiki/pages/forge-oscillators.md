# Forge oscillators and wavetables

OSC A, B and C are identical. `oscillatorCount` in `core/ForgeVoiceParts.h` has been 3 since 2026-09-28. Each has:

- its own table
- OCT, SEMI and FINE tuning
- unison of up to 12 voices (`unisonMax`), with DETUNE and BLEND
- PAN and LEVEL
- two warp stages ([Forge warp](forge-warp.md))
- a MODE, either wavetable or spectral ([Forge spectral oscillator](forge-spectral.md))

SEMI and POSITION are continuous so the matrix can sweep them, but a drag by hand snaps SEMI to semitones and POSITION to frames. FINE is not a continuous parameter: it is declared with an interval of 1 (`{-100, 100, 1}`, `src/ForgeParameters.cpp`), so its knob stops on whole cents, yet the matrix moves it smoothly, because a modulated value never snaps to the interval (see below; `modulatedTuningSuite` checks 25.5 cents).

## OCT steps under modulation

Since 2026-10-13 (commit `e8702e4`) OCT and FINE are matrix destinations as SEMI already was, and OCT moves in whole octaves: `tuningRatio` (`core/ForgePatch.h`) uses `std::round(osc.octave)`. Serum 2's manual (p. 29) suggests an LFO on OCT to jump octaves "without having to count in 12 semitones" and keeps smooth sweeps for CRS; Forge has no CRS and SEMI is its continuous coarse pitch, so OCT steps and FINE does not. Nearest rather than floor, so a bipolar LFO steps symmetrically. The rounding has to live in `tuningRatio`: a destination's offset goes through `NormalisableRange::convertFrom0to1`, which does not snap to the parameter's interval of 1 (the same reason FINE moves smoothly under modulation). Unmodulated patches are unchanged, since OCT then always holds a whole number ([Forge modulation](forge-modulation.md)).

## The built-in ten

The built-in table holds `SINE TRI TRAP SQR PULSE THIN SAW HUMP ORGAN VOX` (`core/ForgeShapes.h`). The order is deliberate: POSITION crossfades neighbouring frames, so each frame is a relative of the one before.

`waveShape` fills `builtInWavetable()` once per process and is not on the render path. If a formula change seems to do nothing, the table predates it: restart rather than reload the plugin.

The saw is rotated half a cycle, as Serum stores it, so the display shows its edge. The LFO saw deliberately is not, because an LFO ramp must reset at the cycle boundary.

## Band-limiting

`Wavetable` (`core/ForgeWavetable.h`) keeps 2048-sample frames plus band-limited copies. Each copy is cut by FFT, zeroing the bins above the limit and their mirrors; forgetting the mirrors is the classic bug.

There are three copies per octave (`wavetableLevelsPerOctave`), giving 26 levels and about 50 KB per frame. With one copy per octave, two notes a tone apart could differ by half their harmonics.

The voice reads `levelFor(hz * 1.05 * headroom)` with Catmull-Rom interpolation. The extra 5% allows for the sharpest unison member, and warps add their own headroom.

Level 0, the frame as authored, is what the panel draws. The voice reads whichever level the note allows. Do not "fix" the display to match, or it would change with every note.

## Tables from elsewhere

- **The TABLE tab** draws on frames. A stroke rebuilds only its frame (`publishFrame`), and `tableEditSuite` checks the result matches a full `publish`. Undo is the panel's and is lost when the editor closes. Its toolbar ends with the table field, then NEW, RESET, LOAD and SAVE (`ui/ForgeTablePanel.h`). A choice in the field, NEW, RESET and LOAD each take an undo step (NEW and LOAD even if their dialog is cancelled); SAVE takes none, since writing a file changes nothing undo could restore.
- **Importing a `.wav`:** the frame size comes from Serum's `clm ` chunk, otherwise 2048. JUCE hides that chunk, so the code walks the RIFF. Other sizes are resampled, and tables longer than 64 frames (`maxEditableFrames`) are thinned evenly. The table is titled after its file, upper-cased (`tableNameOf`). Ten 16-frame factory tables in `tables/` are generated by `make-tables.py`.
- **NEW** names a file in `tables/user` first, then `Processor::newTable` writes one silent frame and imports it, so the table is listed and SAVE has a target from the start. **SAVE** (`Processor::saveTable`) writes the frames, retitles the table after the file and publishes, so a saved built-in stops reporting itself as built-in to POSITION. It writes straight over a file only when `tableSaveTarget` finds exactly one entry of that title inside `tables/user`; a factory table, the built-in ten or two files of one name go through a save-as dialog instead.
- **Writing** (`writeTableFile`, `core/ForgeTableFiles.h`) produces the bytes `make-tables.py` does: RIFF, fmt, `clm `, data, 32-bit float mono at 44.1 kHz, so Serum reads the frame size. It writes a `TemporaryFile` and moves it into place ([juce::File::createOutputStream appends](juce-output-stream-appends.md)).

Tables travel in presets and host state as deflated, base64 `TABLE` nodes ([Forge presets and state](forge-presets-and-state.md)).

## The table field

Each wavetable oscillator has a field in a 22 px strip along the top of its display, and the TABLE tab has the same one; all four share one list ([Forge editor (panel)](forge-editor.md)). Its arrows step through the list; a click opens `ui::tableMenu`: the built-in ten, a separator, then the tree with each folder a submenu, ticked along the path to the playing table. `core/ForgeTableFiles.h` is the disk side. `tableRoot()` walks up from the binary to `tables/` (`tableRootAbove`, ten folders at most) and falls back to `Documents/Rhino Forge/Tables` in a packaged build. In a plugin the binary is the plugin's own file, inside its bundle, and the source tree is eight folders above it, three more than for the standalone. Until 2026-10-13 the walk stopped after eight steps, one short, so the VST3 listed only the built-in ten while the standalone listed the whole tree, and LOAD's dialog, which starts at the same root (`lastFolder`, `ui/ForgeTablePanel.h`), opened at home; `tableLibrarySuite` now finds the factory tables from both builds' paths. `listTables` puts the built-in first, then walks depth-first with each folder's subfolders before its files, in natural order, `*.wav` only, at most 8 deep, skipping dot folders.

**The table is not a parameter.** It travels in a preset as frames, so the list is only what is on disk now, and the playing table is matched to an entry by title (`tableEntryIndex`). An untouched table is the built-in entry. A drawn-over built-in is titled CUSTOM and matches nothing, as does a preset's own table or one loaded from outside the root; the field then shows the title (`FxSelector::caption`, `chosen = -1`) and its right arrow steps onto the first entry. A drawn-over file table keeps its file's title, so it still matches.

**`tables/user/` is git-ignored** (`.gitignore`). NEW and SAVE write there, so a developer's own tables sit beside the factory ones as one more submenu and never reach a commit. `tables/README.md` documents the folder for users.

`tableLibrarySuite` (`tests/ForgeTestsTable.cpp`) covers the file format and round trip, NEW, SAVE, the listing order, matching, save targets, the menu's ids and the strip geometry.

## The hand-off

`WavetableStore` (`core/ForgeTableStore.h`) publishes a pointer that the audio thread loads once per block. A counter is odd while a block runs. After a publish, an even counter frees the old table at once, and an odd one parks it. All of it is deliberately `seq_cst`. Never hold a `const Wavetable*` across a publish ([Hold ids, not pointers](ids-not-pointers.md)).

A parked object is freed by the next publish or by `collect()`, which the editor's timer calls on both stores (`src/ForgeEditorInput.cpp`). Until commit `2cc79de` it collected only the table store, so a replaced spectral sample, up to about 20 MB, stayed in memory until the next publish. With the editor closed, only a publish collects.
