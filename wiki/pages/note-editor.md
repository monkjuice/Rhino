# Note editor (StepGrid)

`StepGrid` edits the notes of the MIDI clip the editor is pointed at, `Session::pattern()`. A document with no MIDI track has no such clip: `Session::hasPatternClip()` says so, every note edit refuses with a message (a velocity edit included), and the grid draws an empty editor. It is one class across nine units in `native/src/ui/notes/`, its folder since 2026-10-13: `StepGrid.cpp`, `StepGridPainter.cpp`, `StepGridGestures.cpp` (pointer), `StepGridEditing.cpp` (selection, region, clipboard, modal tools), `StepGridMenu.cpp` (the right button's menus, commit `4783232`, 2026-10-25), the velocity lane's `StepGridVelocity.cpp`, `StepGridVelocityGestures.cpp` (which also holds the keyboard's hover) and `StepGridVelocityPainter.cpp` (since 2026-10-16), and `StepGridTools.cpp` (the tools panel's commands, commit `2220948`, 2026-10-26). Private helpers are in `StepGridInternal.h`, and the lane's arithmetic is in `VelocityLaneGeometry.h`, a pure header. Its model side is `SessionNotes.cpp`, with `SessionNoteChop.cpp` (the chop) and `SessionNoteAudition.cpp` (the preview) since commit `f2ae477`, and `SessionNoteTools.cpp` (Reverse, Legato, Humanize) since `2220948`. Since `4a6a17b` it also has `SessionClipLoop.cpp`, for the [clip Loop switch](#the-loop-switch). It opens in the shell's lower pane when a MIDI clip is double-clicked, and its first appearance in a run raises the pane to at least `StepGrid::openingHeight`, 327 px since commit `c257d42` (309 px from `d872f0b`, 293 px from `363af51`) ([Drawing](#drawing), [App shell and control bar](app-shell.md)). Since commit `4783232` (2026-10-25, a UX audit of the editor; a change this page dates 2026-10-25 without a hash is that commit, the audit's second round, the same day, is commit `f2ae477`, the same day's fixed row height, scrolling drum rows and marquee repaint are commit `d872f0b`, the 13 px rows with no scrollbar `c257d42`, and a drum clip's assigned-key rows and the Alt + wheel row height `3418c1b`) it says what a command did or why it refused ("Copied 3 notes", "Copy or cut notes first", "No room: a clip holds at most 512 steps in the note editor") through `StepGrid::status`, which `app/MainComponent.cpp` points at the readout as it does the arrangement's.

## Gestures

The pointer follows the rule `SelectionInput.h` shares with the arrangement ([Pointer and selection rules](pointer-and-selection.md)):

- **Double-click** an empty cell to create a note. With Alt it goes where the pointer is, to a sixteenth of a step, one step long or as long as the gap before the next note on its row allows (`addNoteOffTheGrid`, `f2ae477`). A plain drag sweeps a marquee; Ctrl toggles a note, Shift adds.
- **B** (or the footer button) toggles draw mode: the pointer becomes a pencil, a press paints on empty cells or erases on a note, and the drag keeps doing whichever it started. Each stroke is one undo step (`beginNoteGesture`/`endNoteGesture`). Erasing is draw mode, the Delete key or the menu's Delete; Live's double-click-to-delete was considered and left out, so as not to open another accidental-delete path.
- **The right button opens a menu and never erases** (2026-10-25, `StepGridMenu.cpp`). It used to erase in either mode, so every right-click meant as a question cost a note. It takes what it lands on as a press would: an unselected note becomes the selection, one inside the selection keeps it. Over a note, or its marker in the velocity lane, `noteMenu()` (headed with the note's name, the pad's on a drum clip, or "n NOTES") offers cut, copy, paste, duplicate, delete, transpose, Chop (On Grid, as Ctrl+E cuts, or 2, 3, 4, 6 or 8 Parts, for notes on any pitch; until `f2ae477` it was Divide, one pitch only), fill to clip end, select all, and the Draw Mode and Velocity Lane toggles, each labelled with its key. Over an empty cell `gridMenu()` ("D3, STEP 13") offers Add Note (what a double-click does), paste, select all, the two toggles and Loop Clip; over empty lane the same without Add Note. On empty space the selection stays and the insert line moves to the clicked step, so the menu's Paste lands there. The keys, the lane's divider and its gutter open nothing; the ruler opens its own menu (below). Items arrive through `showMenuAsync` and call the existing commands, so each is one undo step, as its key is.
- **Ctrl+E chops** the selected notes, Live's Chop Note(s) on Grid (`f2ae477`, at the user's request): every note, on any pitch, is cut at each step line inside it, in one undo step ("Chop notes") that stays open while Ctrl is held, which the gesture timer checks. With Ctrl still down, a left press anywhere starts `Gesture::chop` (commit `c6da530`), which moves and selects nothing. Dragging up adds a part to every chopped note and dragging down takes one away, a part per 12 px from the press (`chopPixelsPerPart`), and the pointer is the up-down cursor while the chop is open. Ctrl and the arrows step it too. Releasing the button leaves the chop open, because `mouseUp` and `~StepGrid` do not end its note gesture; letting go of Ctrl, another press, another key or any wheel turn ends it. Each note's count starts at its own grid count and is held to 1-32, and a step no note can follow is not taken. Every count is cut afresh from the notes as they were (`chopSources`; `chopPieces` is the last cut), so coming back to the grid count gives the grid cut back. The badge over the first note shows its count. A one-step note chopped on the grid stays whole, where the divide the chop replaced split it in two. That divide, `Session::redistributeNotes` (one pitch's span spread into equal retriggers), is now called only by `ClipWindow.inc`. In `f2ae477` the mouse moving with no button down counted the parts; the user corrected that the same day, and `c6da530` made it the drag. The editor always consumes Ctrl+E (since `4783232`): a refusal used to return false, and the key reached `MainComponent::keyPressed`, where Ctrl+E splits the arrangement's clip at its line, so Ctrl+E with nothing selected cut the clip. It now says "Select notes to chop".
- **Holding V** with Up/Down or the wheel changes the selected notes' velocity by 1 MIDI step (it worked in percent until 2026-10-16). **Ctrl+Up/Down** changes it by 10 when no chop is open, and Ctrl+Shift+Up/Down by 1. Up/Down alone transposes, with Shift for an octave; on a drum clip whose rows are its keys they go a row, a pad, at a time, and Shift twelve rows (commit `3418c1b`, [Note editor drum rows](note-editor-drum-rows.md#moving-notes)).
- **Left and Right** move the selected notes a step along the clip, Alt by a sixteenth of one, as one undo step ("Nudge notes", through `Session::moveNotes`, which clamps at the clip and against other notes); with nothing selected the key is not the editor's. Shift+Left/Right still resizes (2026-10-25).
- **The wheel** scrolls the rows, and Shift or Ctrl zooms the steps, or the rows over the keys. **Alt and the wheel**, anywhere over the editor (grid, keys or velocity lane), make the rows a pixel taller a notch up and a pixel shorter a notch down (`nudgeRowHeight`, commit `3418c1b`, at the user's request; Alt and the wheel scrolled like the plain wheel before). Those zooms and the keys dragged sideways are the only things that change a row's height ([Drawing](#drawing)), and a drum clip's rows scroll too, a pad at a time (commit `d872f0b`; [Drum rows](#drum-rows)). Since `f2ae477` Ctrl and the wheel always zoom, and any wheel turn ends a chop. Before `4783232` they started a divide, which chopped the selected notes for anyone reaching for the zoom, and from then until `f2ae477` they adjusted one Ctrl+E had opened. A sideways wheel or trackpad swipe scrolls along the clip, as in the arrangement; it used to scroll the pitch. With no scrollbar since commit `c257d42`, that swipe, the middle-button pan, a drag's autoscroll at the edge and the zoom are how the steps travel; nothing was added in its place, so a mouse with no sideways wheel uses the middle button or the zoom.
- **Moves and resizes snap; Alt frees them** (`f2ae477`). A move lands the grabbed note's start on a step line once the pointer has travelled half a step, and leaves the note where it is until then, so a drag meant to change the pitch cannot pull an off-grid note onto the grid. The grabbed note (`movingNoteState`), not `movingNotes.front()`, is the anchor. With Alt a move goes in sixteenths of a step, which was the default before. A resized right edge lands on a step line, at least the first past the note's start, and a left edge on one short of the end; with Alt the edge follows the pointer, and the old free sixteenths inside a note's first step are gone. Both read Alt from each event, and `modifierKeysChanged` reapplies it while the pointer is still. The user was unsure what a "grid setting" would be: the grid is the step size, the 1/16, 1/32 or 1/64 box in the control bar, and no snap control was added.
- **Clicking a key selects its pitch** (`selectPitch`, on the release of a keyboard press that never travelled 3 px, `f2ae477`): every note of that pitch in the clip, on screen or not. Shift adds them. Ctrl takes them out when all of them are selected already, and adds them otherwise; Live does that with Shift, but Ctrl is the grid's toggle. Dragging the keys still zooms and scrolls them and selects nothing.
- **The ruler's right button opens a LOOP menu** (`rulerMenu`, `f2ae477`): Loop Clip (Ctrl+L), Double Loop Length (from the same start, past the clip if need be, because the loop is the song's) and Clear Loop, the last two only with a manual loop. It cleared the loop on the spot before. The arrangement's ruler still does, and whether it should get the same menu was put to the user.
- **A note dragged below the rows** is held to the lowest row (`moveDraggedNotesAt`), so it keeps following the pointer while the pitch scrolls; until 2026-10-16 it froze where the pointer left the rows. Since commit `3418c1b` that includes the spare room under rows that all fit: the clamp is the last row's bottom, not the area's.
- **F** fills the selected notes to the clip's end, plain F only, so Ctrl+F gets past the focused editor to the browser's search (commit `bac4059`).
- **The middle button pans** (commit `0725daa`, as the arrangement does): `Gesture::pan` and `panView` in `StepGridGestures.cpp` carry the steps by the pixels travelled (`stepScroll`, clamped to the clip) and the rows by whole rows (`lowestVisiblePitch`, setting `manualPitchScroll`). The anchors are absolute, so a pan that hits the clip's start comes back exactly. Drum rows pan both ways since the rows stopped stretching (commit `d872f0b`); until then they panned only sideways, pinned to the bank. The pan answers first in `mouseDown`: before, a middle press fell through to the left-button paths and carried a note or resized the keys. It edits nothing. It opens no note gesture (`mouseUp` returns early, the destructor skips `endNoteGesture`) and runs before `dragPosition` is recorded, so the gesture timer never autoscrolls it. `NotePan.inc` holds it.
- **The key under the pointer is lit and named** (2026-10-25). `hoveredPitch` is the row under the pointer, over the cells or the keys, the marker under it in the lane, or the note in hand during a move, a resize or a marker drag (`pitchNamedAt`). `paintKeyboard` draws it last: since commit `363af51` the key fills with `palette::noteBody` and its name stands in the names' column on a `noteBody` tag at least 13 px tall (`keyTagHeight`), in `palette::keyHoverText`; on a drum clip the pad's row lights with its name centred. The column names only the Cs (and nothing on rows under 8 px, which no row has gone since commit `3418c1b`), so the tag is how any other pitch is read. It follows moves, drags, autoscroll and the wheel, and goes out on exit and over the ruler. `keyHoverArea` repaints the key's row and one either side; `PartialRepaint.inc` lights a key so its culled-against-unculled comparison covers the tag. The hover light is drawn over the light of a key the track is playing ([Keys the track is playing](#keys-the-track-is-playing)).
- **Nothing marks focus** (2026-10-25). The 2 px cyan frame round the panel and the wash over the ruler while the editor held the keys were removed because the user found them annoying; the arrangement never drew any. `focusLost` still ends Ctrl+E and held V. Focus needs a desktop peer, so no scenario checks this.

## Preview

A headphones button beside the loop button in the top-left corner, both 22 px, is Live's Preview switch (`f2ae477`; `StepGrid::PreviewButton`, a `TextButton` whose `paintButton` draws the loop button's box with a headphone glyph). With it on, a note sounds through the open clip's own track, its instrument and every effect after it, armed or not and with the transport stopped: a key while it is held, a note when it is pressed and again at each new pitch while it is carried, a draw-mode stroke once per row, and a double-click add. `mouseUp` and `~StepGrid` stop it.

The model side is `SessionNoteAudition.cpp`: `noteAuditionEnabled`, `setNoteAuditionEnabled`, `startNoteAudition(pitch, velocity)`, `stopNoteAudition()` and `auditionedPitch()`. One note sounds at a time. It goes in through `te::AudioTrack::injectLiveMidiMessage` on the track holding the clip, and the note-off goes to the same track, found again by its `EditItemID`, so a clip switched or a track deleted in between leaves no note hanging. The engine lets only the message thread make that call, and the note lands a message-loop turn late on a block boundary. That jitter ruled the call out for the DJ decks ([DJ decks play live through the track's chain](dj-decks-play-live-through-the-track.md)) and is nothing for one note under the pointer. The booth's knob-held preview used the same call from 2026-10-10 to 10-12; its commit, `2abe9e0`, notes that the monitoring route tried before it delivered nothing. Unlike the browser's audition, a second audio callback that reaches no track ([Browser and library preview](browser.md)), this plays the track's chain. The switch is a machine preference (settings key `noteAudition`, off by default, never read or written under the test runners), and `changeListenerCallback` keeps the button showing it. Only `NoteGrid.inc` has exercised it, headless: nobody has listened to it in the app yet.

## Keys the track is playing

Since commit `4a6a17b` (2026-10-27; the user asked to "highlight the key you're playing on the midi editor"), every key the open clip's track is playing lights up in `palette::keySounding`, the playhead's blue. The source can be the clip under the playhead, the typing keyboard, a MIDI keyboard, the Push or the preview. A white key lights across its whole width. A black key lights only across its own 60 % width, so it never reads as the white key beside it. On a drum clip the pad's row lights and its name turns `keyHoverText`.

- **Where the keys are read.** They come from the hidden DJ input, `DjTrackInjectorDevice` at plugin index 0 ([Device chain order](device-chain-order.md)). Every note the track plays passes it first, so this one tap covers every source, including a hardware keyboard on a Linear curve, which the engine reads directly and Rhino never sees ([Keyboard velocity curves](keyboard-velocity-curves.md)). Two alternatives were rejected:
  - composing the lights in the UI from the clip's notes under the playhead plus the inputs Rhino routes itself, which misses those ports and would be a simulation;
  - adding another hidden device, which would shift every raw plugin index again.
- **How the keys cross threads.** `devices/infra/HeldKeys.h` keeps the keys lock-free, in two `std::atomic<uint64_t>` words for "down" and two for "struck". On the audio thread, `hear` sets a key on note-on and clears it on note-off (velocity 0 counts as off), and an all-notes-off or all-sound-off releases everything. `take()` on the message thread returns down | struck and clears struck, so a note that starts and ends inside one block still lights for exactly one frame.
- **What the device hears.** The injector hears the chain's MIDI at the top of `applyToBuffer`, before a bound deck's notes join, so deck notes light nothing. It hears nothing while `context.isRendering`, so a bounce or an export lights nothing. Its keys are cleared by `midiPanic` (a stop's `releasePlayingNotes` and the edit panics), by `initialise`, and by a buffer's `isAllNotesOff`.
- **How the editor reads them.** `Session::takePatternKeysDown()` (`SessionNoteAudition.cpp`, "the other way round" from the preview) reads `DjTrackInjectorDevice::takeKeysDown()` on the open clip's track. `StepGrid::updateSoundingKeys()` runs on every display refresh from `updatePlayhead`, which does not run while the editor is hidden. It keeps a `std::bitset` and repaints the `keyHoverArea` of each key whose light changed. On the first read after the editor was hidden (`visibilityChanged` sets `soundingKeysStale`), or after it switched clips, the read is thrown away, so keys struck while it was not looking do not flash.
- **Timing (not measured in the app).** The tap sees a block when the audio thread processes it. That is ahead of the latency-adjusted playhead by about a block plus the output latency, so a key may light a frame or so before the playhead line reaches its note.

`tests/Arrangement/scenarios/NotePlayingKeys.inc` plays the injector by hand a block at a time, as `TrackMeters.inc` does. It checks:

- a white key lights across its width in the playhead's blue, and a black key lights narrower;
- a key goes dark on note-off, and a note inside one block lights for one frame only;
- a velocity-0 note-on counts as off;
- a stop's panic and an all-notes-off clear the keys;
- a render lights nothing, and another track's notes light nothing;
- a key struck while the editor was hidden is not lit.

`RHINO_NOTE_PLAYING_KEYS_SNAPSHOT=<png>` writes the editor with a white key and a black key lit, on a looping clip. Nobody has watched it in the running app yet.

## The Loop switch

Live's clip Loop: a clip dragged longer in the arrangement repeats its loop, and while the clip loops the editor shows and edits only the loop. Since commit `640d90c` the switch is the large first control of the [tools panel](note-editor-tools-panel.md#clip-the-loop-switch), and its click calls `StepGrid::toggleClipLoop()` (`StepGridTools.cpp`). In `4a6a17b` it was a small toggle in the footer (`clipLoopButton`). That toggle is gone, so the footer again holds only Draw and Velocity, and its hint starts at 132 px. The ⟳ button over the keys is a different control and stays as it was: it sets the song's loop over the clip. The rules are in [Clip Loop switch](clip-loop.md).

## The playhead and the ruler

Since `4a6a17b` the playhead and the ruler map time through the model. `Session::patternStepAt(seconds)` measures from the clip's start, and on a looped clip it wraps and phases by the offset. `StepGrid::secondsForClipStep` and `clipStepForSeconds` (`StepGridGestures.cpp`) map the ruler linearly onto the pass the clip starts in, using `patternStepAt(clipStart)` as the phase.

Before that, `playheadXForTime` used (edit beat − clip start + offset) mod clip length. On a clip trimmed from its left edge (split or pasted) it ran ahead by the offset whenever the offset was not a whole multiple of the clip length. The ruler's click-to-seek had the inverse error, so the two agreed with each other but not with the notes.

The song-loop band and its ruler drag (`timelineTimeForLoopStep`, `loopXForTimelineTime`) use the new mapping only on a looped clip and keep the whole-clip fraction otherwise. `showTimeSpan` maps a span in a later pass back to the same steps in the first. `ClipLoop.inc` checks the playhead step and x in a second pass.

## Drawing

Since `f2ae477`, the keyboard since `363af51`, and the rows' height and placement since `d872f0b`, `c257d42` and `3418c1b`:

- **Narrow keys beside a column of names** (commit `363af51`, after a screenshot of another DAW's piano roll the user sent). `labelWidth` stays 54 px so the loop and preview switches above still fit: a 28 px names' column (`keyLabelWidth`, room for C#-2 on the hover tag) on the editor's `palette::sideSurface`, then 24 px keys (50 px before) and a 2 px gap, black keys 60 % of them. Only each C is named, in `uiFont(9)` and `palette::textDim`, right-aligned against the keys, on rows at least `octaveLabelRowHeight` (8 px) tall, which since commit `3418c1b` is every row; the rule that named every key, on the key, from 15 px rows is gone. The whole strip, column included, is still the keyboard to the pointer (`isOverKeyboard`). Drum rows are pads, still drawn and named across the whole strip. `NoteGrid.inc` checks it on rows zoomed to 16 px, since a taller pane no longer makes them taller.
- **A row keeps one height; the pane decides how many show** (commit `d872f0b`, at the user's request: what does not fit is scrolled to, or the pane is made taller). `rowHeight()` is `baseRowHeight` over `pitchZoom`, 13 px at the default zoom (11 px until commit `c257d42`, when the user asked for 2 px more), on piano and drum clips alike. Since commit `3418c1b` it is held to 8-18 px, `baseRowHeight` less or plus `rowHeightReach` (5) (`minimumRowHeight`, `maximumRowHeight`; 7-33 px before). Only the user's own zoom changes it: Alt and the wheel a whole pixel a notch, the line under the pointer held still (`nudgeRowHeight`; the user asked for ±5 px), or the keys dragged sideways, or Shift or Ctrl and the wheel over them, which share the same range. A larger `pitchZoom` is still a thinner row. `computePitchRowCount()` counts every row reaching into the rows' area, `ceil(rowAreaHeight / rowHeight)`, up to `lineCount()`: 128, the whole MIDI range, unless a drum clip's rows are fewer (`maxPitchRows` was 48, with a floor of 8, before `d872f0b`). Until then the rows stretched to fill the area, sixteen at the default zoom, so dragging the pane resized every row; `363af51` had only made them open 2 px taller (`openingRowHeight`, gone). `openingHeight` is sixteen rows of `baseRowHeight` plus header, lane and footer, so exactly sixteen whole rows: 327 px since `c257d42` (309 with 11 px rows and a scrollbar, 293 before). `octaveLabelRowHeight` (8 px) is now the zoom's floor too, so the octave names always show; it still sets how much room the velocity lane must leave the rows. A scenario's editor height now sets which rows exist, and its top row may be a sliver whose centre lies in the ruler, so scenarios size their editors for whole rows and press only those ([Writing Rhino tests](writing-rhino-tests.md), rule 20). `VelocityLaneLayout.inc` checks height and count, and the lane ending at the footer, at every pane height from 112 to 400 px and both step zooms. `NoteGrid.inc` checks Alt and the wheel: a pixel a notch over the grid and over the lane, stopping at five either way, and back to 13 px.
- **Rows stand on the lane, unless they all fit.** `rowsTop()` is the lesser of `headerHeight` and `headerHeight + rowAreaHeight - rows × rowHeight` (the lesser since commit `3418c1b`). When every row fits, as a drum clip's few mostly do, they hang from the header with the spare room below, like the end of a list, and `cellHit` and `pitchNamedAt` find nothing in that room; the two placements meet at the boundary, so nothing jumps. Otherwise they stand on the lane, so the row a pane cuts short is the top one, clipped at the ruler (`paint` narrows its clip to the rows' area once the ruler is drawn, `paintKeyboard` clips the keys to the same area), and the bottom row is always whole. The bottom, because `lowestVisiblePitch` was already the anchor: a pane grown from its top edge, the shell's divider, uncovers pitches above without moving a note, and a drum clip's first pad, the kick on the bank's lowest note, is never the sliver. Every y-to-row mapping goes through `rowsTop()` (`cell`, `lineAtY`/`yForLine`, `cellHit`, `pitchNamedAt`, `keyHoverArea`, the chop badge); one that assumes rows start at `headerHeight` is off by the sliver. The top row line stays at the ruler's edge.
- **The automatic pitch window** (`automaticLowestPitch`) puts a piano clip's highest note on the top whole row, never on the sliver above it.
- **No horizontal scrollbar** (commit `c257d42`, at the user's request; the arrangement keeps its own). The `juce::ScrollBar` is gone, not hidden: `StepGrid` is no longer a `ScrollBar::Listener`, and `scrollBarMoved`, `horizontalScroll` and `scrollHeight` (14 px) went with it. `timeAreaHeight` is the height less header and footer, and the playhead's strip trims the footer only, as `UiProfile.cpp`'s does. `syncHorizontalScroll()` keeps its name because tests and the units call it, but only holds `stepScroll` inside the clip. What it buys: the rows' area no longer changes with the zoom. A clip wider than the view used to bring the scrollbar in over the footer, taking 14 px from the lane and the rows, which could fold the lane at short heights and made `zoomAt` and `showTimeSpan` re-run the change listener when the row count moved. Those checks are gone, and `resized()` updates the Velocity button, since the lane folds by the pane's height alone. How the steps travel instead is under [Gestures](#gestures), the wheel.
- **The ruler counts bars and beats** from the clip's own start, as Live's clip ruler does (`paintRuler`). A beat is the signature's note value: `stepsPerBeat()` is `editorStepResolution()` (16, 32 or 64) over the denominator (1 to 16), which always divides, and `stepsPerBar()` is that times the numerator, so 6/8 counts eighths, as the arrangement does ([Transport, tempo and loop](transport.md#time-signature-and-metronome)). Each bar is numbered at its line, and each beat reads bar.beat while it is at least 36 px wide. Bars are numbered every 1, 2, 4... once a numbered bar would get under 30 px. Zoomed in until a beat is wider than half the view, with steps at least 36 px, the steps between read bar.beat.step too; a deep-zoom snapshot showed the ruler blank before that. Ticks stand at its foot, taller at a bar than at a beat. They are rounded with `juce::roundToInt`, as the grid's lines are: `std::round` put them a pixel off the beat line when x fell on .5, which `NoteGrid.inc` caught. A label either edge would cut is skipped.
- **The shading follows the beat.** The cells alternate per beat and the velocity lane's columns follow; both used to alternate every 4 steps whatever the resolution, so at 1/32 they alternated every eighth note. Vertical lines take three shades: bar, beat and step. A new time signature moves every line without moving a note, so `changeListenerCallback` repaints when `stepsPerBeat` or `stepsPerBar` changes (`shownStepsPerBeat`, `shownStepsPerBar`).
- **Black-key rows are darker**, except on a drum clip, whose rows are pads. The colours are `palette` tokens ([Colours and typography](colours-and-typography.md)).
- **Notes are shaded by velocity.** The colour (`noteBody` or `noteSelected`, and the bright right edge) moves 0.6 × (1 − (v − 1) / 126) of the way to `palette::noteCell`, so 127 is the full colour and 1 still stands clear of the grid. The lane's markers keep their colour, since their height shows velocity. A velocity-only change used to repaint nothing in the grid. `rebuildVisibleNotes` now walks the old and new `visibleNotes` side by side, looking up to 8 notes ahead, and repaints each note whose velocity changed; `refreshNoteVelocities` repaints them during a lane drag.
- **The pitch-position bar** at the right edge, which looked like a scrollbar and could not be dragged, is gone.

`NoteGrid.inc` holds all of it, with the snapping, the chop, the key clicks and the preview; `RHINO_NOTE_GRID_SNAPSHOT=<png>` writes the editor partway through, the preview switched on ([Seeing the UI without taking the screen](headless-ui-snapshots.md)).

## Velocity lane

Below the rows, a lane shows a marker for every note of the clip, including notes scrolled out of the pitch window, in MIDI 1-127. It is modelled on Live 12's velocity editor. A marker can be dragged, a group dragged with it, values painted in draw mode or swept up with a marquee, and every gesture is one undo step announced once. The lane folds away rather than leave the rows less than 128 px, sixteen rows of 8 px. Hovering a grid note lights its marker, and hovering a marker lights its key. Layout, model and gestures are in [Note editor velocity lane](note-velocity-lane.md).

## Tools panel and the scale highlight

Since commit `2220948` (2026-10-26) `NoteToolsPanel`, a 168 px sibling of the grid down its left in the lower pane, holds the scale highlight and three Live utilities. The scale moved there from the shell's "Scale: off / C Major ... B Minor" combo and now takes any root and twelve scales (`StepGrid::setScaleHighlight(bool shown, int root, MusicalScale)`); Humanize, Reverse and Legato act on the selected notes, or every note of the clip, in one undo step each, by rules in `SessionNoteTools.cpp`. Since commit `640d90c` (2026-10-27) the panel opens with the clip [Loop switch](#the-loop-switch). Details in [Note editor tools panel](note-editor-tools-panel.md).

## The step region and the insert line

Copy, cut, duplicate and delete act on a span of steps, the region (`stepSelection`): the arrangement's [region editing](region-editing.md) rule, measured in steps. Copy keeps the region's width, so rests at either end survive. A paste replaces the notes it covers, lengthening the clip if needed, rather than hunting for empty space.

Since 2026-10-25 a paste lands on the **insert line**, `insertStep`, Live's insert marker: kept apart from the region and the only line drawn (`paintInsertLine`; `regionFromNotes` is gone). A click on empty cells or lane, a ruler click, a marquee (at the start of what it swept), `showTimeSpan` (at the span's start) and a right-click on empty space put it down. A copy moves it to the end of the copied region, a cut to its start, and a paste or duplicate to the end of what was pasted, so pastes in a row lie end to end. Escape clears it, and so does the editor showing another clip (`changeListenerCallback` compares `session.pattern().itemID` with `shownClip`). With no line, `pasteStep()` lands just after the selected notes, else at step 0. Ctrl+D captures into a local `NoteClipboard` (`captureRegion`, then `pasteNotes(clipboard, atStep, actionName)`) and leaves the clipboard alone, as the arrangement's duplicate does; it used to go through `copySelection`.

Why: a paste used to land at `stepSelection.start`, and selecting notes makes the region their own span, so Ctrl+C then Ctrl+V wrote the copy exactly over its source, and the paste's replace rule removed the source. Nothing visible changed, and dragging the "copy" away left a hole, which the user reported as copy and paste "cutting on the first paste". The arrangement keeps the old rule, a paste at the selection's start that a second paste replaces; the user knows ([Region editing](region-editing.md#in-the-note-editor)). `NoteClipboard.inc` holds the line after a copy, the untouched source, a second paste beside the first, the line surviving a session change, Ctrl+D leaving the clipboard alone, and a paste with no line going after the selection.

Copy, cut and `effectiveStepRegion` read the selected notes through `laneNoteFor`, which covers every note in the clip, not only the visible rows. Until 2026-10-16, a selected note outside the pitch window was deleted by cut but left out of the clipboard. Ctrl+A could already reach that case, and the velocity lane made it a one-click case. A cut-and-paste round-trip test now holds it.

The marquee anchors in steps and lines (the pitch on a piano clip, `selectionAnchorLine`), not pixels: a drag past an edge scrolls the view from the gesture timer, and a pixel anchor would travel with it, dropping notes that had scrolled out.

## Showing a swept span

Since commit `4bd0f45` (2026-10-24) a sweep across part of the open MIDI clip in the arrangement is shown here, as Live's Clip View shows the part of a clip selected and zooms to a time selection. The arrangement names the clip primary and reports the span ([Region editing](region-editing.md#one-selection)); the shell calls `StepGrid::showTimeSpan(start, end)` (`StepGridEditing.cpp`) when the clip is the pattern clip, whether the editor is showing or not, so the Clip toggle then opens it on that part.

- **Frame.** Seconds become the clip's steps through the tempo map, held to the clip's own end, which can fall short of the grid's last step. `stepZoom = clamp(steps / span, 1, max(8, steps / 16))`: the upper bound is the deepest view the editor otherwise shows, since a long clip opens at steps/16, deeper than `zoomAt`'s 8. The scroll frames the span exactly when the zoom reaches it and centres it when it is narrower than the deepest view.
- **Select.** Every note overlapping the span, at any pitch, the step region set to the exact span, and the insert line at its start.
- **Order.** The selection is set last, because a rebuild reads the region off the notes again; until commit `c257d42` the new zoom could bring in the scrollbar, change the row count and run one (`changeListenerCallback`) inside `showTimeSpan`. A hidden editor whose step count is stale is rebuilt first: otherwise the catch-up rebuild when it is shown sees a new step count and resets the zoom to the new length's default. `showTimeSpan` also sets `shownClip` itself, so that catch-up does not take the new line for one left over from the previous clip and clear it.
- **Pitch is left alone.** The automatic pitch window already fits the clip's notes; scrolling to the part would set `manualPitchScroll`, which turns the automatic fit off for later clips too.

`RegionMove.inc` checks the framed span, a one-step span centred, the insert line at the span's start, and a grid framed while hidden inside a parent component that keeps its frame and its line once shown.

## A note that began before the window

A MIDI clip plays a window into its sequence, set by its offset; cuts and trims move the window, never the notes ([Clips never overlap](clip-placement.md)). Tracktion plays a note that began before the window and ends inside it, from the clip's start: `MidiList::createDefaultPlaybackMidiSequence` keeps any note ending after the window's start, and `addToSequence` emits its note-on at `std::max (0.0, downTime)` (checked upstream at `4536d8a`). The arrangement drew it, but the grid and the velocity lane skip any note starting before step 0 (`rebuildVisibleNotes`, `rebuildLaneNotes`), so until commit `1818c5b` (2026-10-24) such a note sounded with nothing in the editor. It was found on a clip whose window opened 3/64 of a beat (23 ms) after a note began; how the clip got that window was not recovered, since moves are not logged.

`Session::editorNotes` (`SessionNotes.cpp`, helper `shownStartStep`) now reports a note crossing the window's start as starting at step 0, with the length it sounds for. No UI file changed: the grid, the lane and the note clipboard all read `editorNotes`. Edits act on what is shown:

- `resizeNote` and `fillNoteToClipEnd` measure the length from the shown start and keep the hidden part before the window.
- A chop (`chopNotes`, Ctrl+E since `f2ae477`) cuts from the shown start and drops the hidden part, as `redistributeNotes`, the divide before it, does, so no piece lands where the clip cannot play it.
- Moving the note left is refused by `moveNotes`' existing clamp. Moving it right lands it under the pointer, because `moveDraggedNotesAt` asks for the distance from where the note is shown.
- A note wholly before the window plays nothing, keeps its negative start and stays off the grid.

Showing what plays follows [Displays draw from the DSP](displays-draw-from-the-dsp.md). Live's manual does not say what Live does here. Silencing the note was the alternative, and it was not taken. `tests/Arrangement/scenarios/ClipWindow.inc` holds it: the note is shown at step 0 for its sounding length, in both `visibleNotes` and `laneNotes`, a resize keeps its true start, and a `redistributeNotes` divide into two gives halves at steps 0 and 2.

## Drum rows

When the open clip's track plays drums (`Session::isPatternDrums`), the rows are pads. Since commit `3418c1b` they are only the keys its [Drum Rack](drum-rack.md) has assigned plus the keys its notes are on. A pad emptied under notes keeps a row named for its pitch, and Live's Fold is left for a separate control. The rows are mapped through lines, move notes row to row, hold still under a gesture, open on the bank the rack's face shows and scroll like a piano clip's (since `d872f0b`). All of it, with the decisions behind it and the tests, is in [Note editor drum rows](note-editor-drum-rows.md).

## Pitfalls

- **Size.** Its row-addressed caches span 512 steps × 128 rows since commit `d872f0b`. The float ones, `noteLengths` and `noteStartOffsets`, are 256 KB each, so they are `std::vector`s on the heap, beside a second pair (`nextLengths`, `nextStartOffsets`) that a rebuild fills and swaps so that it allocates nothing; held inline at 48 rows they made one `StepGrid` about 200 KB. The three bitsets, 8 KB each, stay in the object. In a test scenario still create one with `std::make_unique` ([A CTest SegFault may be a stack overflow](stack-overflow-reports-as-segfault.md)).
- **One timer serves every gesture.** Drags, marquees, strokes and the modal tools (Ctrl+E, held V) share the grid's gesture timer. Ending a modal tool stops the timer only when no other gesture is running (`finishSubdivision`, `finishVelocityAdjustment`, since 2026-10-16), so a stroke keeps autoscrolling after one ends. In the other direction, `mouseUp` leaves the timer running while hold-V or a subdivision (the chop) is active, because the timer is what notices V or Ctrl being released.
- **Clip the time axis at the keys' edge.** Zoomed in, one step can be wider than the 54 px keyboard (`labelWidth`), and scrolled part-way into a step, its cells, notes, step lines and ruler number start left of the keys. Nothing clipped them, so until 2026-10-25 they were painted over the whole keyboard and under the loop button, and the keys vanished. `StepGrid::paint` now wraps the header numbers, cells, notes and row and step lines in `saveState` and `reduceClipRegion({labelWidth, 0, gridWidth, timeAreaBottom})`, and restores before `paintKeyboard` (moved after the grid, because it sets its own font and the numbers need `uiFont(10)`) and before `paintVelocityLane`, which clips itself and draws its gutter left of `labelWidth`. A ruler label that either edge would cut is not drawn (the tail of 21 read as 1 beside the loop button), and the Ctrl+E chop badge is held right of the keys. The arrangement had the same bug with clips over the track cards ([Arrangement view](arrangement-view.md#rules-worth-knowing)). `NoteKeys.inc` compares the key column and the loop button at a whole-step scroll and at `stepZoom` 16, `stepScroll` 20.5, and fails with the clip removed; `RHINO_NOTE_KEYS_SNAPSHOT=<png>` writes that state ([Seeing the UI without taking the screen](headless-ui-snapshots.md)).
- **A selection change repaints what it changes** (`setSelectedStates`, since 2026-10-16): the notes it recolours and the lane. The insert line repaints its own two columns in `setInsertStep`. Before 2026-10-16, clicking an unselected note in a grid that already had focus repainted only the footer. The marquee is repainted away when its gesture ends: `mouseUp` repaints `selectionBox` grown by 2 px (commit `d872f0b`). Nothing else repainted where it stood, so the box stayed drawn after release until something painted over it; the lane's marquee already did this in `finishVelocityLaneGesture`. `NoteGrid.inc` checks it by logging the grid's repaints, and fails with the release's repaint taken out ([Writing Rhino tests](writing-rhino-tests.md), rule 19).
- **A row is a line, not a pitch** (commit `3418c1b`). On a drum clip whose rows are its keys, row and pitch convert through `lineOfPitch`, `pitchOfRow` and the other line helpers, never `lowestVisiblePitch + rows - 1 - row`, which is right only while every pitch is a row. The set of rows changes only between gestures, never under a drag ([Note editor drum rows](note-editor-drum-rows.md#lines)).
- **It is welded to `Session`.** Its four files of the time reached into `Session` 101 times (counted 2026-10-03), and `Session.h` pulls in Tracktion. That is why Forge's planned arp pattern editor cannot simply reuse it: first extract a Session-free note-grid header, as `ClipGeometry.h` was.
- **The clip can vanish under it.** `Session::repairPatternClip` is the single place that re-points the editor when its clip goes: by id first, else to the first MIDI clip on the first MIDI track, else to a hidden starter clip it makes there, never onto an audio track ([No track is special for being first](pattern-track.md), [Hold ids, not pointers](ids-not-pointers.md)).
- **The step region does not survive a session change; the insert line does.** Every rebuild (`rebuildVisibleNotes`, run on every session change) calls `setSelectedStates`, which calls `setStepRegionFromSelection`, so a region from a marquee, a click or `showTimeSpan` gives way to the selected notes' span rounded out to whole steps, or to nothing when no note is selected. Until 2026-10-25 a paste read that region, so any change made while no note was selected wiped a click's insert point and the next paste landed on step 0. It now reads `insertStep`, which no rebuild touches. Zoom, scroll and the note selection survive too.
- **Hidden, it waits.** While another face holds the lower pane the grid marks itself stale instead of rebuilding on every change, and skips its playhead every display refresh ([What a change costs the interface](ui-cost-of-a-change.md)).
- **Octave names.** Middle C reads C3, matching Live, Forge and the Drum Rack's pads (`padNoteName` in `core/content/DrumKitFile.h`, which `DrumRackDevice::noteName` calls). Both of the painter's keyboards name rows through `pitchName` in `StepGridInternal.h` (until 2026-10-06, `drumLaneName`). Change `pitchName` and `padNoteName` together or the rows and the pads disagree.

## Not done yet

Of what the audit of 2026-10-25 recommended, `f2ae477` settled all but one: the pitch-position thumb was removed rather than made draggable, and snapping became the default with Alt to free it rather than a new control. Still open: the insert-line rule for the arrangement, whose paste still lands on its source. Whether the arrangement's ruler should open the LOOP menu too was put to the user; its right-click still clears the loop. The preview has not been heard in the app, and nobody has watched the lit keys or used the Loop switch there either.
